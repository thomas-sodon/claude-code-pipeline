Your findings are verdicts in `review/residual-build-ship.json` (beside this file): a JSON object whose `verdicts` array has,
per finding, `n`, `title`, `status`, `priority`, `remaining_change` (the change to make, written by a reviewer who read the

How to work a verdict: verify it against the code first (a reviewer can be wrong; if it does not hold, skip it and say so);
implement `must` and `should` as `remaining_change` says, in the files YOU own; implement `could` only when it is a few
lines; never implement `skip`. Where a `remaining_change` names files you do not own, do your part and list the rest under
follow_ups. Prefer reusing what exists (plan_ref, pr_note, the answers plumbing) over a new mechanism. Keep every behaviour
not named. Add the tests each verdict names (in the test files you own), and keep every existing test passing without
weakening it (change an expectation only where the behaviour it pins changed on purpose, and say so).

Every package also aligns its files with SPEC 1 in the short form a build stage needs: a blocking question includes a
conflict between what the person said (an answer, the framing, a decision a doc tags `(person, ...)`) and what the stage
finds; a person-owned choice no doc, plan or answer settles is asked, never assumed; what the person settled is never
changed (R4); questions name things by title (R5); answers are `{ id, answer, question?, date? }` and the prompt shows the
question text; every `needs_input` relay also says to show the person the result's assumptions and to pass each question
back with its answer and date.
